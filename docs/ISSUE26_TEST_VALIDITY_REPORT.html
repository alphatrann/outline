What mutation testing actually does

Your reading is right: Stryker deliberately injects faults into the production code, then runs the tests. If a test fails, the fault was killed (the tests noticed). If every test still passes, the fault survived (the tests cannot tell the correct code from the broken code). Nothing is "masked": a surviving mutant is a concrete change that the suite is blind to.

  1. Generate mutants. For each mutated file Stryker finds small, local code patterns and creates one broken variant of each, so one mutant is one fault. Here: 695 mutants across 5 files.
  2. Find which tests touch each mutant (perTest coverage). A mutant that no test executes is reported NoCoverage without running anything.
  3. Activate one mutant at a time and run only the tests that execute that line. Any failure or timeout means killed.
  4. Score = (killed + timeout) / all mutants. Here (219 + 1) / 695 = 31.65%.

Why the code looked like gibberish

Recompiling the app 695 times would be far too slow. Instead, Stryker rewrites each file once, embedding every fault as a switch: stryMutAct_9fa48("175") ? <faulty version> : <original>. Before each test run it sets the "active mutant" id, so only that one switch flips. The stryCov_… calls record which tests reach which mutant. The unreadable code is temporary instrumentation, not the faults themselves, and Stryker restores the original files when the run ends (in-place mode keeps a backup in .stryker-tmp). Real example, server/policies/collection.ts line 35: 

original:
  if (!collection || user.teamId !== collection.teamId) { return false; }

what Stryker writes (shortened):
  if (stryMutAct("175") ? !collection && user.teamId !== collection.teamId
    : stryMutAct("174") ? false
    : stryMutAct("173") ? true
    : (!collection || user.teamId !== collection.teamId)) { ... }

With no mutant active, the last branch runs, which is the original logic. With mutant 174 active, the condition is replaced by false, which removes the cross-team check entirely.

Tests added in response

  • documents.move: user who can write the destination but only read the source gets 403 and the document stays put.
  • documents.archive: read-only member gets 403, archivedAt stays null.
  • collections.info: another team's user cannot read an open (ReadWrite) collection.
  • shares.create: another team's user cannot share a document; no share row is created.

All four pass against the unmodified code, so no permission bug was found. The first three fail when their safeguard is removed (re-verified with the same deliberate-breakage procedure).
