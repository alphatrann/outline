4 · The four flows (what to understand)

These are the areas covered by integration tests.

Access and permissions

Sign in→Open collection→Check access→Share
  • Private collection = explicit access only.
  • Guests always need explicit access.
  • Access comes from people or groups.

Read: server/policies/collection.ts · server/routes/api/collections

Document lifecycle

Draft→Publish→Move / archive→Restore
  • Deleting is soft first.
  • Concurrent edits are guarded.
  • Moving keeps the collection tree in sync.

Read: server/commands/documentUpdater.ts · server/models/Document.ts

Revisions

Edit→Wait→Snapshot→Restore
  • Snapshots are made in the background, not on save.
  • Identical content is skipped.
  • Tests must wait for the worker.

Read: server/queues/processors/RevisionsProcessor.ts · server/models/Revision.ts

Search and sharing

Write→Indexed→Search→Share link
  • Title matches rank above body matches.
  • A share link is an unguessable id.
  • Revoking a share cuts public access.

Read: plugins/search-postgres/server · server/commands/shareLoader.ts · server/models/Share.ts

5 · Modules (what the tests touch)

Four building blocks sit under the flows above.

Document

  • The page people write. Has a draft state until published.
  • Belongs to a collection and sits in its tree.
  • Deleting moves it to trash first; archive and restore are separate states.

Read: server/models/Document.ts · server/commands

Collection

  • A folder of documents. Keeps the page tree in documentStructure.
  • Has a default permission, or none when private, plus per-person and per-group grants.
  • Changing privacy or sharing records a permission_changed event.

Read: server/models/Collection.ts · server/policies/collection.ts

Revision

  • A saved snapshot of a document's title and content.
  • Created by a background worker after edits settle, not on every save.
  • Revision.findLatest(documentId) returns the newest one.

Read: server/models/Revision.ts · server/queues/processors/RevisionsProcessor.ts

Search

  • Uses Postgres full-text search on a searchVector column.
  • Results are ordered with ts_rank.
  • Results are filtered by what the searcher may read.

Read: plugins/search-postgres/server/PostgresSearchProvider.ts

6 · How to explore

Pick any action, then follow it down.

  1. Find the route: rg '"documents.update"' server/routes
  2. Read its input rules (schema.ts next to it).
  3. Read the matching file in server/policies.
  4. Read the action in server/commands, then the model.
  5. Read the colocated *.test.ts to see real usage.

Tip: the web app calls the same names. Search the action name in app/stores to see who triggers it.

7 · Tests

  • Unit: yarn test path/to/file.test.ts on a local database.
  • Integration: yarn test:integration starts throw-away Postgres and Redis in Docker.
  • Integration files are named *.integration.test.ts. See server/routes/api/users/users.integration.test.ts.
  • Test helpers: server/test (factories.ts, TestServer.ts, cleanup.ts).
  • Slower than unit tests, so keep them to the four flows above.

Out of scope: social sign-in, file contents, live co-editing, the web UI.
