2. BUG-1 — Concurrent identical documents.update calls create duplicate revisions

Environment

OS / arch macOS 27.0, arm64
Node / Yarn v24.21.0 / 4.18.1
Docker 29.5.2 (Testcontainers: postgres:17, redis:8)
Vitest 4.1.11, project server-integration (serial files)
Outline base pinned SHA 05ef55e, plus local commit f83c131a9

Steps to reproduce

  1. Start the worker (initWorker()) so Bull queues are consumed.
  2. Create a team, user and a published document titled T with text C.
  3. Send two identical requests concurrently: 
    await Promise.all([
  server.post("/api/documents.update", user, { body: { id, title: "T", text: "C", done: true } }),
  server.post("/api/documents.update", user, { body: { id, title: "T", text: "C", done: true } }),
]);
  4. Wait about 3 s, then Revision.count({ where: { documentId } }).

Reproduced 8 / 8 times (log: logs/issue-26/repro.txt). Seen as a failure in 1 / 5 full-suite runs, where the original test fired the two updates back to back without waiting.

Expected

One revision. RevisionsProcessor skips creating a revision when the document equals the latest revision (title and content), so identical updates should collapse to a single row.

Actual

FAIL revisions.integration.test.ts > #revisions (integration)
  > should not create duplicate revisions for identical updates
AssertionError: expected 2 to deeply equal 1      (revisions.integration.test.ts:128)

Two revision rows with identical title and content.

Root cause analysis

server/queues/processors/RevisionsProcessor.ts does a check-then-insert: Revision.findLatest(), compare, then Revision.createFromDocument() in a separate transaction, with no lock. Two events processed at the same time both see "no previous revision" and both insert. The dedup is therefore only reliable when events are processed one after another.

Classification

Axis Rating Reason
Severity Low One extra history row. No data loss, leak or permission bypass.
Priority Low Needs two simultaneous identical API saves. Editor autosave takes the debounced path, not this one.

Matrix action: low / low → normally log only. The fix was small, so it was applied anyway and kept with a regression test.

Fix applied

In RevisionsProcessor, the read-then-insert now runs inside one transaction that first takes a row lock on the document (SELECT … FOR UPDATE OF "document"). A second event for the same document waits for the first to commit, then sees its revision and skips. Revision.findLatest() gained an optional transaction argument so the check runs inside that transaction. The Redis attribution cleanup stays after the commit, as before.

Why a row lock, not an advisory lock or isolation level: the document row always exists, so it is a natural lock target and matches how collections.add_user locks its membership row. REPEATABLE READ gives each transaction a snapshot but does not make one wait for the other, so both would still insert; SERIALIZABLE would need retry handling across the app. An advisory lock stays as the fallback if this lock contends with other document writes.

Pitfall found while fixing: a plain lock: UPDATE failed with FOR UPDATE cannot be applied to the nullable side of an outer join, because the Document default scope left-joins users. The lock is restricted with of: Document.

Test handling

  • The original test was flaky by design (it raced the bug). It now sends the updates sequentially and covers the sequential dedup path.
  • New regression test should not create duplicate revisions for concurrent identical updates fails without the fix (expected 2 to deeply equal 1) and passes with it.
  • shortcut: both tests wait a fixed 2–3 s for the queue to settle, since no job-done signal is exposed; revisit if they become slow or flaky.

FLAKE-2 — "should create a revision asynchronously" asserts the worker has not run

Where revisions.integration.test.ts:77 (from the issue-19 tests, not the new ones); failed once in CI, never locally in about 15 runs
Actual AssertionError: expected 1 to deeply equal +0
Expected Revision.count() is 0 right after documents.update returns, because the worker creates the revision in the background
Root cause The assertion checks that async work has not happened yet. It only holds if the test is faster than the worker; a fast CI runner reverses that. It is a test race, not a product bug.
Classification Severity low (test only, no product impact), priority high (it blocks CI on every PR touching server code) → quick fix
Fix Removed the "not yet created" assertion. The polling (waitForLatestRevision) that follows already proves the revision is created.

Lesson: the 5-run local check did not catch it. CI hardware has different timing, so a green local streak is evidence, not proof, of no flakiness.
